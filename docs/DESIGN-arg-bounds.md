# Design: Per-Argument Bounds for Console Commands

Status: **implemented** (`7ee71cd`: per-argument bounds from `argbounds.csv` and the
one-sided cvar change; the bounds flow through the Config Editor's guided pane and the
Build-A-Bind panels). Records every change needed to make argument
bounds correct for commands that take one or more numeric parameters.

## 1. Problem

The engine never bounds command *arguments*: a `ConCommand` receives its arguments as
strings, and any validation lives inside the handler, invisible to the console. Bounds
we record are therefore **authoring metadata** — they exist to stop the Build-A-Bind
editors from producing a command the game would reject or misread, not to mimic an
engine clamp.

Today that metadata can only describe a *cvar*: the catalog's min/max columns (fields
4/5 of `allcmds.csv`, `res/cfg/schema.md`) hold one min and one max per **row**, and
`cmd::ConVar::hasRange()/minVal()/maxVal()` expose exactly that pair. A command like

    drawline [flt] [flt] [flt] [flt] [flt] [flt]

has six numeric parameters, each of which may need its own (possibly one-sided) bounds.
Nothing in the current data model, catalog format, loader, `ConsoleCommandModel` roles,
or the QML editors can express that. The same limitation means a cvar with only a min
or only a max cannot be recorded either (the loader requires both columns non-empty to
treat a row as ranged).

## 2. Data census (measured 2026-10-13, `res/cfg/allcmds.csv`)

Three numeric populations, two mechanisms:

| Population | Count | Where its bounds live | Mechanism |
|---|---|---|---|
| Commands with documented numeric args | **49** | Companion file (new) | `ArgSpec` per argument |
| Commands whose args are undocumented (`none`) | **~2,656** rows say `none` | Nothing today | In-game verification sweep, then the companion file |
| Numeric cvars (`int`/`flt` value type) | **786 + 467** | Fields 4/5 (existing) | Cvar range, needs the one-sided fix |

Notes from the census:

- Bracketless `int`/`flt` in field 8 occurs **only on cvar rows** (type column empty or
  `cvar`). No `cmd`/`ncmd` row has an unbracketed signature, so the "many more rows"
  impression comes from (a) cvars being numeric and (b) undocumented `none` commands —
  not from inconsistent notation. The fix for (a) is the one-sided cvar change; the
  fix for (b) is verification, not tooling.
- Cvar bounds today: **115 rows carry both min and max**, **35 carry min only** (e.g.
  `mp_maxrounds 0`, `ds_kill_delay 5`), 0 carry max only. The loader's
  `hasRange()` (both required) silently drops all 35 one-sided rows.
- `bool` cvars (1,422) are numeric (0/1) but self-bounding; they need no new storage.

## 3. Decisions (user-confirmed 2026-10-13)

| # | Decision | Choice |
|---|----------|--------|
| D-a | Where bounds live | **Companion file**; `allcmds.csv` stays 10-field/untouched |
| D-b | How a bound is expressed | **Structured rows** (one row per argument), not inline grammar in the usage string |
| D-c | Which rows get data | **Numeric-arg commands only** (49 documented rows today; the undocumented `none` population grows it via the verification sweep, section 9) |
| D-d | How the UI consumes bounds | **New `argsSpec` role**; cvar `MinRole`/`MaxRole` stay as they are |
| D-e | Unverified bounds | **Unbounded editors** — no data means free-form input, matching the engine's accept-anything behavior |

## 4. Companion file: `res/cfg/argbounds.csv`

New resource, headerless, one row per bounded argument of a command. Columns:

| # | Field | Example | Notes |
|---|-------|---------|-------|
| 1 | Command | `load_itempreset` | Exact console name, lowercase-folded by the loader for lookup |
| 2 | Arg index | `0` | 0-based position in the usage signature (`[str] [flt] ...`) |
| 3 | Type | `int` / `flt` | The numeric type the editor should author |
| 4 | Min | `0` | Empty = no lower bound (one-sided max allowed) |
| 5 | Max | `3` | Empty = no upper bound (one-sided min allowed) |

Rules:

- A row without a matching command in `allcmds.csv`, or with an arg index outside that
  command's signature, is skipped with a `qWarning` — the catalog is the shape
  authority; the companion file only annotates it.
- Rows are only ever added after in-game verification (the `load_itempreset`
  0..3 correction is the model for how entries earn their place). No implicit bounds
  are invented anywhere in the pipeline.
- A missing companion file is not an error: the app runs with zero arg bounds.
- `res/res.qrc` gains the file; `res/cfg/schema.md` gains a section documenting it.

### Why a companion file

The 10-field CSV schema is pinned by `catalogRowsHaveTenFields()`, read by
`Lexers::cmdLex`, and regenerated by `tools/csvio.py` + `tools/field_dicts.py`. Adding
columns would break all three for a datum that concerns ~1.3% of rows. A separate file
keeps the existing contract untouched and lets the regen tools treat arg bounds as an
input they must preserve, not something they generate.

## 5. Engine model changes (`src/gamecfg/`)

### `cmd::ArgSpec` (new, in `convars.h`)

    struct ArgSpec {
        int index;          // position in the usage signature
        bool isFloat;       // int vs flt for the editor's spin box mode
        bool hasMin;        // one-sided bounds supported, like ConVar's m_bHasMin/m_bHasMax
        double min;
        bool hasMax;
        double max;
    };

Doubles throughout: int and flt bounds feed the same spin box, exactly like the cvar
`minVal()/maxVal()` pattern already does.

### `cmd::ConCmd`

Gains `const QVector<ArgSpec> &argSpec() const` (empty for commands without bounds and
for all cvars). `GameCfg` fills it after `loadAllCmds()` from the companion file.

### One-sided cvar bounds (promoted to in-scope)

`cmdLex::Token::hasRange()` requires both min and max, which silently drops the 35
min-only cvar rows the census found. Move the cvar path to per-side presence flags
(`hasMin()/hasMax()`) so a CSV row with only one bound keeps it. Same engine
semantics: `ConVar::SetValue` clamps each side independently (`m_bHasMin`/`m_bHasMax`
are independent flags). This lands with step 1 of the rollout; it reuses the same
`ArgSpec`-style per-side representation.

## 6. Catalog loading (`GameCfg`)

- `loadArgBounds()` runs after `loadAllCmds()`, reads `://cfg/argbounds.csv` with
  `cmdLex` (the existing CSV reader — same quoting rules, no new lexer).
- Storage: `QHash<QString, QVector<ArgSpec>> m_argSpecs` keyed by lowercased command
  name; `ConCmd` instances get their vector attached (or look it up through `GameCfg`
  — implementation detail, decided at code time; attaching keeps `allCmds()`
  consumers self-sufficient).
- Validation per row: command must exist in `cmd_map` and be a `cmd`/`ncmd` row, the
  arg index must be `<` the signature's token count, min ≤ max when both present.
  Failures warn and skip the row; they never abort the load.

## 7. `ConsoleCommandModel` changes (`src/ui/`)

- New role `ArgsSpecRole` (`argsSpec`): for a `cmd` row, a `QVariantList` of
  `QVariantMap { index, isFloat, hasMin, min, hasMax, max, optional }` — one entry per
  token in the usage signature, bounds empty when unknown. For cvars the role returns
  an empty list; cvar bounds keep flowing through `MinRole`/`MaxRole` (D-d).
- The `optional` flag is derived from the usage string (`<...>` vs `[...]`), which the
  model already receives via `get_usage()`; the companion file does not duplicate it.
- `findCommand()` includes `argsSpec` in its returned map so the dialog can look a
  command up by name without going through the visible list.

## 8. QML changes (`qml/dialogs/BindEditorDialog.qml`)

`rebuildArgs()` currently builds one editor per usage token and applies the single
cvar `min`/`max` to every numeric editor. It changes to:

- Read `argsSpec` for the selected command. Numeric entries drive spin boxes: `int` →
  decimals 0, `flt` → decimals as today; `hasMin`/`hasMax` set the spin box bounds
  only on the sides present (D-e: no data → free-form editor).
- Commands without an `argsSpec` keep today's behavior exactly (usage-token editors,
  cvar range when the command is also a cvar-like row — unchanged for all 3,776
  unannotated rows).
- `incrementvar` keeps its special-cased free-form min/max/delta editor; its bounds
  are user-authored arguments, not catalog data.

## 9. Tools

- `tools/csvio.py` / `tools/field_dicts.py`: catalog regeneration must treat
  `res/cfg/argbounds.csv` as **preserved input** — it is hand-verified data, never
  generated. Add an explicit guard (refuse to write allcmds.csv if argbounds references
  a command the regenerated catalog lost, so a regeneration cannot orphan rows).
- A tiny authoring aid (optional, nice-to-have): two verification worklists —
  1. catalog commands whose signature contains `int`/`flt` (49 rows today), and
  2. a sampling of `none` commands most likely to take args (the ~2,656-row hole is
     the real undercount; work it by likelihood of bind-relevant use, not exhaustively).

## 10. Tests (`tests/tst_engine.cpp`)

1. Companion loader: valid row attaches bounds; one-sided rows (min only, max only)
   survive; min > max rejected; unknown command / out-of-range arg index skipped;
   missing file tolerated.
2. `ArgsSpecRole`: command with bounds returns per-token specs; cvar returns empty;
   `optional` flags match the usage string.
3. `findCommand` carries `argsSpec`.
4. Existing 10-field pin test untouched (proof the schema did not move).
5. If the one-sided cvar follow-up lands: a CSV row with only min (or only max) keeps
   that side through `ConVar`.

## 11. Docs

- `res/cfg/schema.md`: new "argbounds.csv" section.
- `docs/ARCHITECTURE.md`: catalog contract gains the companion file + "bounds are
  authoring metadata, never engine-enforced" statement; model contract table gains
  `argsSpec`.
- `docs/AUDIT.md` / `docs/ROADMAP.md`: close the finding, note the one-sided cvar
  follow-up.

## 12. Rollout order

1. `ArgSpec` + one-sided cvar fix + companion loader + tests (engine-only, no UI
   change; the 35 min-only cvar rows start surviving).
2. `ArgsSpecRole` + `findCommand` + tests.
3. `rebuildArgs()` consumes the role.
4. Seed `argbounds.csv` with verified rows as they are confirmed in-game
   (`load_itempreset` int 0..3 is the first candidate; `incrementvar` stays excluded).

Each step is independently committable; steps 1–2 add capability nobody consumes yet,
so UI behavior cannot regress before step 3.

## 13. Out of scope

- Rewriting the catalog to JSON/YAML (rejected, D-a).
- Enforcing bounds at save time or rejecting out-of-range configs — the engine
  accepts anything; we only shape authoring.
- Implicit bounds for unbounded parameters (rejected in the preceding discussion).
